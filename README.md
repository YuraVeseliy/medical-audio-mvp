# Медицинский аудиомодуль — учебная часть ВКР

Приложение для Юрия Черных и Михаила Бурундукова: **запись или готовый аудиофайл → русская транскрипция → цитаты для разделов «Жалобы» и «Анамнез» → проверка и правки человеком**.

Контекст ВКР — работа с медицинским диалогом в ОКБ №1. Здесь реализована ограниченная учебная часть цепочки. Это прототип для разработки и проверки подхода; результаты моделей могут содержать ошибки.

## Получить проект с GitHub

Публичный репозиторий: [YuraVeseliy/medical-audio-mvp](https://github.com/YuraVeseliy/medical-audio-mvp). Для чтения и скачивания приглашение не требуется.

```powershell
git clone https://github.com/YuraVeseliy/medical-audio-mvp.git
cd medical-audio-mvp
```

Затем выполните установку из раздела ниже. В репозитории есть код, учебные данные, тесты, результаты экспериментов, [план ДЗ в PDF](docs/Итоговый_план_ДЗ_аудиомодуль.pdf) и [итоговый отчёт в PDF](docs/Итоговый_отчёт_ДЗ_аудиомодуль.pdf). Модели и установленное окружение скачивает `setup.cmd`; готовый многогигабайтный EXE-комплект в историю Git не входит.

Проект опубликован самостоятельным снимком актуального аудиомодуля. Происхождение сохранённых результатов и отличие нового Git-коммита от старых хешей пояснены в [docs/publication.md](docs/publication.md).

## Готовый комплект Windows

Если у вас папка **MedicalAudio_Windows** с MedicalAudio.exe, _internal и .runtime: запустите **launch.cmd** или сам EXE. Python и модели в этом варианте уже включены; setup.cmd не нужен. Переносите всю папку целиком. Первый запуск обработки дольше прогретого; проверенный холодный запуск EXE на учебном файле занял 31.46 с на машине разработки. Другой ПК и настоящий микрофон проверяются отдельно.

В сравнении обнаружен открытый дефект качества D05: модель выбирает вопросы и неверные разделы. Черновик требует проверки и правки. Числа и примеры приведены в docs/final-report.md и experiments/comparison-results.md; автоматическое заполнение для больницы не считается принятым.

## Что можно сделать

- Выбрать устройство и явно начать запись; остановить её и сохранить WAV.
- Загрузить аудиофайл WAV, MP3, M4A, FLAC, OGG или MP4 с аудиодорожкой.
- После завершения записи получить транскрипцию с помощью локальной модели faster-whisper.
- Выбрать предложения для двух разделов локальной моделью Qwen2.5-3B; восстановить цитаты из исходника и перейти к ним. Модель выбирает номера, а не сочиняет текст.
- Исправить тексты разделов, сохранить сеанс в JSON, открыть его и экспортировать текущий результат в TXT.
- Увидеть ошибки загрузки/обработки и предупреждение перед потерей несохранённых правок.

Приложение не ставит диагноз, не проверяет полноту врачебного протокола, не интегрируется с 1С и не определяет автоматически личность говорящего. Телефонный интерфейс и потоковое распознавание во время разговора в этот объём не входят.

## Быстрый запуск из исходников в Windows

Проверенная среда разработки: **Python 3.12 x64, Windows, CPU**. Для первой установки нужен интернет: загружаются Python-пакеты, локальные модели и llama.cpp. Для обработки подготовленных файлов сетевой сервис распознавания не требуется. Модели занимают несколько гигабайт; нужно дополнительное место для окружения и результатов.

1. Распакуйте весь проект в обычную папку, например `C:\Projects\medical_audio_mvp`.
2. Установите Python 3.12 x64 с компонентом Tcl/Tk и Python Launcher, если они ещё не установлены.
3. Запустите `setup.cmd`. Скрипт создаст `.venv`, установит закреплённые зависимости и подготовит `.runtime`.
4. Дождитесь сообщения об успешной подготовке и запустите **`launch.cmd`**.

`launch.cmd` — запуск приложения. `setup.cmd` нужен при первоначальной настройке или изменении зависимостей. Открытие окна само по себе не начинает запись и не загружает модели в память. Первая обработка дольше последующих: модели сначала загружаются с диска.

Если установка прервалась, сохраните полный текст ошибки. Команда повторной подготовки моделей в PowerShell из папки проекта:

```powershell
.\.venv\Scripts\python.exe scripts\setup_models.py
```

Повторная загрузка проверяет уже подготовленные артефакты. Не переименовывайте и не редактируйте файлы моделей вручную. Точные источники, ревизии и контрольные суммы записываются в `.runtime/manifest.json` и дополнительных манифестах подготовки.

## Первый понятный сценарий

1. Нажмите **«Загрузить аудиофайл…»**, выберите `data/audio/dev01.wav`.
2. Нажмите **«Обработать аудио»**. Дождитесь результата; во время обработки не запускайте второй экземпляр на том же порту.
3. Сверьте исходную транскрипцию с `data/references/dev01.txt` и прослушайте файл самостоятельно.
4. Посмотрите «Жалобы», «Анамнез» и список цитат. Нажмите на цитату — соответствующее место выделится в транскрипции.
5. Исправьте текст раздела. Нажмите **«Сохранить сеанс…»** и сохраните JSON в выбранную вами папку.
6. Выполните **«Экспорт TXT…»**, затем **«Новый сеанс» → «Открыть сеанс…»** и убедитесь, что сохранённые правки восстановились.

Проверяйте не только совпадение слов: модель может выбрать неверный раздел, пропустить отрицание или нужную реплику. Наличие цитаты в источнике не доказывает медицинскую правильность результата. После ручной правки список исходных цитат сохраняет происхождение автоматического результата; он не является доказательством добавленного человеком текста.

## Запись микрофона — отдельная проверка

Нажмите «Обновить устройства», выберите устройство, затем «Начать запись». После «Остановить и сохранить…» микрофон останавливается до выбора пути сохранения. Если отменить выбор пути, уже записанный звук остаётся доступным для сохранения или удаления.

Для домашней работы используйте только вымышленные разговоры, записанные вами с согласия участников. Сначала прослушайте файл и убедитесь, что обе стороны слышны. Наличие кнопки и автоматической проверки состояния не подтверждает качество записи конкретного микрофона в больнице.

В текущем быстром наборе 11 проверок; отдельно сохранён один инструментальный сценарий GUI и эксперименты с настоящими моделями. Это разные виды доказательств.

Карточки личной проверки студентами: [docs/manual-tests.md](docs/manual-tests.md). Их результаты, исполнитель и дата должны быть заполнены после вашего реального прогона. Программные проверки агента и испытания на синтетическом голосе не заменяют эту работу.

## Где находятся модели и данные

| Папка | Содержимое |
|---|---|
| `.runtime/models/` | Локальная ASR-модель и GGUF-модель извлечения |
| `.runtime/llama/` | Windows CPU-версия llama-server и его DLL |
| `.runtime/licenses/` | Уведомления о лицензиях подготовленных компонентов |
| `.runtime/manifest*.json` | Источники, версии и контрольные суммы загрузок |
| `data/` | Вымышленные сценарии, эталонные тексты и синтетическое аудио для технических экспериментов |
| `reports/` | Реальные логи проверок, среда, результаты сравнений и дефекты |
| `docs/` | План ДЗ, объяснения решений, карточки ручных проверок |

Папки `.venv` и `.runtime` не хранятся в Git и не входят в архив исходников. Не переносите только `MedicalAudio.exe`: готовому комплекту нужны соседние файлы Python-runtime, DLL и папка `.runtime`.

При работе приложение использует локальный HTTP-сервер llama.cpp на `127.0.0.1:8081`. Текст не должен отправляться на внешний адрес. Локальное выполнение само по себе не решает вопросы хранения персональных данных, доступа к компьютеру и удаления файлов: в этом учебном комплекте используются вымышленные сведения. Сеансы сохраняются обычными JSON/TXT без шифрования в выбранном вами месте.

## Команды для разработки и проверки

Все команды выполняются в PowerShell **из корня проекта**.

Быстрые автоматические проверки поведения приложения:

```powershell
.\.venv\Scripts\python.exe scripts\check.py
```

Лог: `reports/checks/tests.log`; сводка с версией среды и хешем исходников: `reports/checks/summary.json`. В этих проверках внешние модели и устройство могут заменяться контролируемыми ответами. Они проверяют поведение программы, а не точность медицинского распознавания. Конкретный состав проверок смотрите в `tests/` и итоговом отчёте.

Проверка согласованности установленных Python-пакетов:

```powershell
.\.venv\Scripts\python.exe -m pip check
```

Обработка файла без графического окна:

```powershell
.\.venv\Scripts\python.exe -m audio_mvp.cli data\audio\dev01.wav --out user_sessions\dev01
```

У этой команды те же этапы обработки. В выбранной папке появляются JSON-сеанс, TXT и сведения о запуске. `user_sessions/` исключена из Git и упаковки исходников.

Отдельная папка моделей или порт для графического приложения:

```powershell
.\.venv\Scripts\python.exe -m audio_mvp --runtime-path D:\MedicalRuntime --port 8082
```

Сравнение моделей и аналогов — отдельный эксперимент. Изучите `experiments/analog-plan.md`, данные и параметры запуска в сохранённых результатах. Повторный запуск изменяет файлы результатов: сохраняйте старый прогон отдельно. Не переносите выводы с коротких синтетических записей на реальные приёмы.

## Как работать вдвоём

1. Оба используют одну версию исходников и зависимостей. Для каждого изменения создаётся отдельная ветка и небольшая задача.
2. До кода записываются ожидаемое поведение и проверка. Где применён TDD, реальный цикл «красный тест → код → зелёный тест» подтверждается логами; обычный запуск тестов после готового кода сам по себе не является TDD.
3. Перед объединением выполняются быстрые проверки; второй участник читает изменения и проверяет понятный пользовательский сценарий.
4. После исправления сначала повторяется сценарий дефекта, затем проверки связанных функций. Первое подтверждает исправление, второе — регрессия.
5. Изменения требований и вопросы к заказчику фиксируются в задаче. Работающий инкремент обсуждается с заказчиком; реальное согласование записывается отдельно.

Конфигурация GitHub Actions находится в `.github/workflows/checks.yml`. Наличие файла не означает, что удалённый CI уже выполнился: это проверяется по конкретному запуску в GitHub. Локальный комплект подготовлен в отдельной ветке; публикация и слияние выполняются отдельно.

## Подготовка архивов и portable-комплекта

Исходный архив без моделей, окружения и пользовательских сеансов:

```powershell
.\.venv\Scripts\python.exe scripts\package_source.py
```

По умолчанию ZIP и JSON с контрольной суммой создаются в `../../output/`. Внутри ZIP есть перечень файлов с SHA256. Исходный ZIP требует установки через `setup.cmd`.

Сборка Windows portable выполняется отдельно на Windows с подготовленным окружением:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build_portable.ps1 -InstallBuildTool
```

Скрипт использует PyInstaller 6.16.0, создаёт новую папку сборки, копирует проверенные runtime-артефакты по манифестам и записывает контрольные суммы. В ней запускается `launch.cmd` рядом с `MedicalAudio.exe`. До проверки готового комплекта на другом компьютере переносимость остаётся неподтверждённой. Сборку не следует выполнять одновременно с замерами производительности моделей.

Если возникла ошибка, сохраните версию комплекта, действие, ожидаемый и фактический результат, полный текст ошибки и условия: ОС, Python или EXE, CPU/RAM, выбранные модели и имя вымышленного файла. Это позволяет повторить проблему и проверить исправление.

## Условия выбранной модели

GGUF Qwen2.5-3B Q4_K_M занимает около 2.1 GB; faster-whisper-small — около 0.49 GB. Проверенная машина имеет 16 GB RAM; работа на меньшем объёме памяти отдельно не измерялась. Qwen3B предоставляется по **Qwen Research License**; полный текст находится в `.runtime/licenses/Qwen3B-LICENSE.txt`. Комплект подготовлен для некоммерческого учебного исследования. Первоначальная 1.5B остаётся в журналах неудачного эксперимента, но не нужна рабочему приложению.

В portable-версии тот же командный сценарий доступен через `MedicalAudio.exe --cli путь.wav --out папка`. Это оконная сборка, поэтому результат проверяется по созданным session.json/result.txt/run.json, а не по консольному выводу. Не запускайте обработку одновременно с замерами аналогов.
