# Как устроен проект и как объяснять решения на защите

Дата подготовки: 24.10.2026. Документ дополняет [итоговый план](homework-plan.md) и объясняет понятия на примерах нашего аудиомодуля. Здесь изложены основания решений и способ их проверки. Фактические результаты, версии, измерения и ограничения следует смотреть в итоговом отчёте и приложенных журналах. Описание практики в этом документе само по себе не доказывает, что она уже выполнена.

Авторы ВКР: Юрий Черных и Михаил Бурундуков. Заказчик ВКР — ОКБ №1. Научный руководитель — Захарова Ирина Гелиевна. Тема относится к формированию протокола осмотра пациента в отделении реанимации; в предоставленной презентации названы хирург и анестезиолог. Ревматология не является областью этой версии проекта.

## 1. Что именно требуется в первом ДЗ

Основание — лекция 4, слайд 36. Семь требований задания нельзя заменить демонстрацией одного интерфейса или большим количеством тестов.

| Пункт задания | Что мы должны уметь показать и объяснить |
|---|---|
| 1. Разработка ПО в рамках ВКР | Работающую выбранную часть, её вход, выход, пользователя, ограничения и способ запуска |
| 2. Модели, методологии и методы с аргументацией и подтверждением | Почему выбран такой процесс; чем он отличается от альтернатив; какие действия действительно подтверждают применение |
| 3. Сравнительная оценка с аналогами, измерение показателей | Как выбраны сопоставимые продукты, как получены числа и в каких пределах верен вывод |
| 4. Тестирование с объяснением методов | Какие риски и требования проверяет каждый метод; почему набор достаточен для заявленного объёма |
| 5. Ручные и автоматизированные методы | Реально выполненные действия человека и отдельно воспроизводимые автоматические проверки |
| 6. Отчёт о тестировании | Версию, условия, результаты, реальные проблемы, повторные проверки и оставшиеся ограничения |
| 7. Презентация | Понятное студентам объяснение продукта и доказательств. Презентацию по этому комплекту студенты готовят самостоятельно |

В критериях оценки отдельно названы Agile, сравнение, методы разработки, ручные проверки, автоматические проверки и первый отчёт. Указание Agile не делает Scrum обязательным. В тексте ДЗ нет установленного количества тестов, требования обучить собственную нейросеть, провести все виды тестирования или непременно обнаружить дефект. При этом выбрать удобные термины без их реального применения недостаточно.

## 2. Пользовательская проблема, цель и границы

Пользователь — врач, который беседует с пациентом и готовит протокол осмотра. Препятствие — сведения из разговора приходится переносить в форму, одновременно сохраняя внимание к осмотру. Возможное последствие — дополнительная работа с документом и риск потери части сказанного. Размер затрат и частота ошибок именно в ОКБ №1 нашим экспериментом пока не установлены. Статистику другой страны или амбулаторного приёма нельзя выдавать за измерение работы этого отделения.

Цель учебного модуля: дать возможность локально записать или загрузить вымышленный русскоязычный диалог, получить его транскрипцию и подтверждённые исходным текстом сведения в разделах «Жалобы» и «Анамнез», затем проверить, исправить и сохранить результат. Ожидаемая польза — уменьшить объём ручного переноса сведений. Реальное сокращение времени нужно измерить на пользовательском сценарии; наличие такой цели ещё не доказывает эффект.

Проверяемая гипотеза может быть сформулирована так: «При одинаковом требовании к качеству результата приложение помогает подготовить два раздела быстрее, чем выбранный исходный порядок работы». Для проверки необходимы одинаковые задания, критерии готовности и реальные пользователи. Без этого допустим вывод о технической работоспособности, но не о доказанной экономии времени врача.

| Граница | Содержание |
|---|---|
| Вход | Запись микрофона или поддерживаемый аудиофайл; затем полученный из него текст |
| Работа | Локальное распознавание речи, выделение цитат и распределение по двум разделам |
| Выход | Доступная для проверки транскрипция, сведения по разделам, правки пользователя, экспорт |
| Время обработки | После завершения записи; потоковое распознавание во время разговора отдельно не обещано |
| Учебные данные | Вымышленные диалоги; синтезированные и человеческие записи различаются в отчёте |
| За пределами версии | Диагноз, рекомендации, проверка полноты медицинского алгоритма, интеграция с 1С, мобильный клиент и внедрение в больницу |

Отдельная законченная часть ВКР удобна для ДЗ, потому что у неё можно определить вход, выход и критерии проверки. Это не меняет общего замысла ВКР. Утверждения о результатах относятся к реализованной части.

Особенно важно различать две полноты. **Полнота извлечения** показывает, сколько сказанных нужных сведений найдено. **Полнота опроса** показывает, получены ли обязательные сведения по согласованному медицинскому алгоритму. Если об аллергии вообще не спросили, из текста нельзя извлечь ответ. В учебной версии не создаём медицинский алгоритм самостоятельно ради теста.

## 3. SRS, требования и их проверяемость

SRS — спецификация требований к программному обеспечению: описание того, что должна делать программа и каким ограничениям удовлетворять. Для небольшого проекта достаточно компактного документа. В нашем комплекте эту роль выполняют требования и приёмка в итоговом плане вместе с уточнёнными сценариями.

Спецификация должна охватывать функции, качества, интерфейсы и ограничения. Функция отвечает на вопрос «что делает программа»: например, импортирует файл. Требование к качеству задаёт свойство выполнения: длительная операция не прекращает обновление интерфейса. Интерфейс — способ взаимодействия с человеком, файлом, устройством или компонентом. Ограничение — заданная граница выбора: локальная обработка на Windows. Нельзя приписывать локальной программе HTTP API только ради полноты схемы.

| Атрибут | Зачем нужен | Пример применения |
|---|---|---|
| Корректность | Требование соответствует потребности и предметной области | Не называть учебный раздел утверждённой формой ОКБ без подтверждения |
| Проверяемость | Можно установить выполнение | Вместо «удобный интерфейс» — конкретная задача и наблюдаемое поведение |
| Полнота | Описаны необходимые случаи и ограничения | Уточнено поведение при ошибке чтения файла |
| Недвусмысленность | Исполнители понимают требование одинаково | Различаются «запись идёт» и «обработка идёт» |
| Непротиворечивость | Требования не исключают друг друга | Локальная обязательная функция не зависит от облачного API |
| Приоритет | Понятно, что необходимо для сценария | Запись и импорт обязательны; вспомогательный экспорт сеанса имеет свой приоритет |
| Атомарность | Отдельное поведение можно принять отдельно | Ошибка модели и её последствия выделены в явную проверку |
| Модифицируемость | Изменение можно внести без противоречивых копий | Один актуальный перечень требований и журнал изменений |
| Прослеживаемость | Видна связь решения с основанием и проверкой | FR04 → извлечение → тест/эксперимент → результат прогона |

Для требования фиксируем ID, формулировку, источник, приоритет, проверку и статус согласования. ID помогает связям, но номер без этих связей ещё не обеспечивает прослеживаемость. Приоритет отличается от иерархии: более подробное требование не обязательно менее важное.

Источник наших учебных требований — обсуждение со студентами и предоставленная презентация ВКР. Это не равнозначно утверждению всех деталей врачом. Изменение требований сопровождаем причиной, влиянием на код, данные и проверки. Согласованный предел времени или качества записывается до итогового измерения. Если предела пока нет, фиксируем измеренное значение и отсутствие основания объявить его приемлемым для больницы.

Разработка тестов начинается вместе с требованиями. Например, к FR07 о восстановлении после ошибки сразу можно подготовить сценарий: внешний распознаватель отказал → приложение показало сообщение → следующая попытка доступна. Сам текст сценария можно проверить до реализации.

Изучить: лекция 2, слайды 4–13; лекция 2.1, слайд 29; лекция 4, слайды 10–16. Дополнительно: [пример структуры SRS в руководстве NASA](https://swehb.nasa.gov/spaces/SWEHBVC/pages/140640750/SRS%2B-%2BSoftware%2BRequirements%2BSpecification). Масштаб процесса NASA копировать не требуется.

## 4. Жизненный цикл и выбор модели

Жизненный цикл описывает работу от возникновения потребности до завершения использования продукта. Модель жизненного цикла задаёт организацию и связи этой работы. Одни и те же виды деятельности присутствуют в разных моделях.

| Этап | Что означает у нас | Результат |
|---|---|---|
| Планирование | Определить потребность, учебный объём, сроки, ресурсы и риски | План и границы |
| Требования | Уточнить функции, условия, ошибки и приёмку | Спецификация и сценарии |
| Проектирование | Разделить ответственность и продумать взаимодействие | Компоненты, данные, состояния |
| Реализация | Написать код и подключить локальные средства обработки | Исполняемая версия |
| Проверка | Проверить требования, ошибки, качество и ограничения | Результаты и дефекты |
| Развёртывание | Подготовить зависимости, модели и запуск на целевом ПК | Воспроизводимая установка |
| Эксплуатация | Наблюдать реальное использование и исправлять проблемы | Обращения и эксплуатационные измерения |
| Завершение | Определить прекращение поддержки, экспорт и удаление данных | Решение о завершении и обращении с данными |

Приёмка предшествует решению о выпуске в заданном контексте. UAT — пользовательское приёмочное тестирование: представитель пользователей выполняет задачи и оценивает выполнение согласованных потребностей. Проверка разработчика и оценка преподавателя не заменяют приёмку врачом. Эксплуатация в больнице в рамках текущего учебного комплекта не утверждается.

Для нашего объёма выбрано инкрементное развитие с итерациями. **Инкремент** добавляет законченную возможность: сначала импорт и транскрипция, затем разделы и работа с результатом, затем запись и стабилизация. **Итерация** — повторное уточнение уже выбранного решения: например, после измерения изменить представление источников или обработку ошибки. Порядок инкрементов может уточняться ради ранней проверки существенного риска.

| Модель | В чём её особенность | Как оцениваем для нашего проекта |
|---|---|---|
| Каскадная, или водопадная | Основные этапы и результаты заранее планируются последовательно | Удобна при устойчивых требованиях. У нас часть интерфейса, данных и условий ещё уточняется; ранняя обратная связь по работающим частям полезнее одной окончательной поставки |
| Каскадная с возвратами | Сохраняется последовательная основа, но предусмотрено исправление ранних результатов | Возможна, но не так точно описывает выбранные поставки отдельных возможностей |
| Итерационная | Решение последовательно уточняется | Нужна для доработки поведения; сама по себе не обещает добавление новых возможностей |
| Инкрементная с итерациями | Возможности накапливаются, существующие решения уточняются | Соответствует нашему плану законченных поставок и обратной связи |
| Спиральная | Содержание следующего цикла определяется существенными рисками и способами их уменьшить | Полный процесс не вводим. Ранние технические пробы заимствуем осмысленно; обычный список рисков не доказывает применение спирали |
| V-модель | Работы по требованиям и проектированию связаны с соответствующими уровнями проверки | Берём прослеживаемость и раннее планирование проверок внутри инкрементов. V-модель не сводится к движению «от общего к частному» |
| Прототипирование | Создаётся пробное решение для ответа на вопрос | Используем как приём исследования; прототип может применяться в разных моделях |
| Большой взрыв | Неформальная организация при слабом предварительном определении работ | Плохо помогает обеспечить воспроизводимые доказательства для этого ДЗ |

Изменения возможны и в каскадном процессе, но могут потребовать пересмотра ранее принятых результатов. Неизвестный микрофон — техническая неопределённость; изменение нужных разделов — изменение требований. Оба обстоятельства стоит исследовать, но не смешивать.

Выбор модели обосновывается условиями, а не утверждением, что остальные модели устарели. Подходящая фраза для защиты: «Мы постепенно поставляем работающие возможности и уточняем их по проверкам. Поэтому выбрали инкрементное развитие с итерациями. Требования и критерии внутри текущей задачи фиксируем, а изменения проводим явно».

Изучить: лекция 2, слайды 15–28; лекция 3, слайды 7–15. О спиральной модели: [материал SEI о разработке на основе рисков](https://www.sei.cmu.edu/library/spiral-development-experience-principles-and-refinements-spiral-development-workshop-february-9-2000/).

## 5. Agile, организация работы и инженерные практики

Agile — ценности и принципы гибкой разработки. Они направляют принятие решений, но не задают единую доску, длительность задачи или язык программирования. GitHub предоставляет инструменты. Инкрементная модель организует развитие продукта. Kanban-практики помогают управлять задачами. TDD и CI определяют конкретные действия разработки. Это совместимые уровни решений.

В нашем проекте преобладает адаптивный акцент: часть требований уточняется по работе с результатом. При этом фиксированные сроки ДЗ, доступные ресурсы и критерии текущего инкремента сохраняются. Участники могут пересмотреть приоритеты на следующую работу, но не подменять проверку бесконечным «дорабатываем, пока понравится».

Четыре ценностных направления применяем так:

| Направление | Наше применение | Что должно подтвердить применение |
|---|---|---|
| Взаимодействие людей | Обсуждать непонятное с напарником и заказчиком | Решения и уточнения по конкретным вопросам |
| Работоспособный результат | Показывать исполняемый сценарий после инкремента | Версия, которую можно запустить и проверить |
| Совместное уточнение потребности | Проверять с пользователем форму результата | Фактические замечания и изменение решения по ним |
| Готовность изменить план | Менять приоритет по новым сведениям | Причина изменения, влияние и обновлённая задача |

Документация, инструменты и план при этом полезны. Их объём должен помогать работе и проверке. Источник: [Манифест Agile](https://agilemanifesto.org/iso/ru/manifesto.html).

Все двенадцать принципов полезно знать, но в отчёте отделять намерение от наблюдения:

| Принцип своими словами | План применения | Доказательство или ограничение |
|---|---|---|
| 1. Польза появляется рано | Поставлять законченные сценарии | Запускаемые версии; полезность врачу требует отдельной оценки |
| 2. Новые требования рассматриваются | Заводить изменение, оценивать влияние | Журнал решений, а не незаметная смена критерия после теста |
| 3. Поставки происходят регулярно | Завершать небольшие инкременты | Даты и содержание версий |
| 4. Предметная сторона участвует | Выносить вопросы к заказчику на обсуждение | Двухнедельные встречи названы студентами; отсутствие ежедневного участия не скрываем |
| 5. Людям дают условия и ответственность | Доступ к проекту, понятные задачи, самостоятельная работа | Реальные назначения и отзывы участников; не выдумывать участие Михаила в выполненных агентом действиях |
| 6. Обсуждение помогает быстрее уточнять | Разбирать неоднозначность голосом и фиксировать решение | Протокол конкретного обсуждения, когда оно состоялось |
| 7. Прогресс виден по работающему продукту | Считать завершённые возможности | Демонстрация; число строк и тестов само по себе не показатель прогресса |
| 8. Темп должен быть поддерживаемым | Ограничивать незавершённую работу | Реальная нагрузка; выполнение одного комплекта агентом этого не доказывает |
| 9. Качество помогает изменениям | Проверки, простые границы компонентов, рефакторинг | Изменения кода и результаты проверок |
| 10. Лишнюю работу сокращают | Держать согласованный учебный объём | Явные исключения; функции не добавляются ради терминов |
| 11. Команда участвует в организации | Совместно выбирать задачи и решения | Фактическое участие обоих студентов |
| 12. Способ работы пересматривается | После инкремента обсудить затруднения | Одно конкретное улучшение процесса и его последствие |

Полный перечень для изучения: [принципы Agile](https://agilemanifesto.org/iso/ru/principles.html). Применение всех принципов на практике нельзя подтвердить одним документом, особенно до участия пользователей.

**Kanban-практики.** Поток — движение задач от готовности к работе до завершения. Для него задаём состояния «очередь», «готово к работе», «в работе», «проверка», «завершено»; слово «готово» не должно обозначать одновременно начало и конец. Ограничиваем число одновременно выполняемых основных задач и явно отмечаем блокировки. Перед началом понятны требование и проверка, перед завершением есть результат и необходимые свидетельства. Если заявлять полный метод Kanban, нужны также явное определение потока и наблюдение показателей: незавершённая работа, пропускная способность, возраст задачи и время цикла. Одна доска ещё не доказывает выполнение метода. Источник: [The Kanban Guide](https://kanbanguides.org/the-kanban-guide/).

**Scrum.** Полный Scrum предусматривает конкретные ответственности, события, артефакты и обязательства. Двухнедельный созвон с заказчиком не образует Scrum. Для двух студентов сейчас выбран более простой способ управления задачами. Если позднее вводить Scrum, потребуется осмысленно выполнять его структуру; GitHub останется лишь инструментом. Источник: [Scrum Guide](https://scrumguides.org/scrum-guide.html).

**TDD.** Сначала формулируем проверяемое поведение, пишем тест и наблюдаем ожидаемое падение. Затем добавляем достаточно кода, чтобы тест прошёл. После этого при необходимости улучшаем структуру, сохраняя поведение. Цикл маленький и происходит внутри реализации, а не после готового инкремента. Пример: новый сеанс не должен сохранять текст старого → тест демонстрирует проблему → код изменён → тест проходит. Красный тест новой функции не выдаём за дефект уже выпущенного продукта. Факт порядка действий подтверждают сохранённые логи или история. Источник: [TDD у Мартина Фаулера](https://martinfowler.com/bliki/TestDrivenDevelopment.html).

Подстановка известного ответа внешнего распознавателя позволяет проверить передачу данных и состояние. Она не подтверждает точность реальной модели. Внутренние компоненты не следует заменять имитациями так широко, чтобы тест проверял только собственные подстановки.

**CI.** Непрерывная интеграция предполагает частое соединение небольших изменений и автоматическую проверку результата. Конфигурация GitHub Actions делает запуск возможным, но её наличие не доказывает удалённый прогон. Локальный журнал доказывает локальное выполнение. Работа вдвоём подтверждается реальными последующими изменениями обоих участников. Две долгие ветки, объединённые перед защитой, плохо соответствуют этой практике. Источник: [Continuous Integration](https://martinfowler.com/articles/continuousIntegration.html).

**Рефакторинг.** Изменяем внутреннее устройство кода, сохраняя наблюдаемое поведение. Например, выносим повторяющееся преобразование результата в одну функцию. Добавление новой функции или изменение медицинского смысла результата сами по себе рефакторингом не являются. Источник: [определение рефакторинга](https://refactoring.com/).

**Прототипирование.** Сначала задаём вопрос: «Сможет ли локальная модель обработать пример на этом ПК?» или «Понятна ли врачу связь раздела с исходной цитатой?». Делаем минимальную пробу, наблюдаем результат, принимаем решение. Не каждый готовый инкремент является прототипом: у пробы есть конкретная неопределённость, которую нужно уменьшить.

| Другой подход | Что это даёт | Что заявляем в нашем проекте |
|---|---|---|
| XP | Согласованный набор инженерных и командных практик | Отдельные практики TDD, CI и рефакторинга; полный XP не заявлен |
| Lean | Сокращение ненужной работы и потерь при создании ценности | Используем идею ограничивать лишний объём; «аккуратность» сама по себе не определяет Lean |
| FDD | Организация разработки вокруг небольших пользовательских возможностей в составе конкретного процесса | Наличие функций не означает применение полного FDD |
| OpenUP | Определённый итерационный процесс с жизненным циклом и ролями | Итерации не делают наш процесс автоматически OpenUP |
| MSF | Семейство рекомендаций и моделей организации разработки Microsoft | Не требуется для Python или Windows; целиком не вводится |
| DSDM | Подход к адаптивной поставке с управлением сроками, приоритетами и участием бизнеса | Это не динамическое программирование; целиком не вводится |
| Cleanroom | Процесс с формальным обоснованием корректности и статистическим тестированием использования | Наших обычных проверок недостаточно для такой заявки |

Эти альтернативы нужны для осмысленного выбора, но не для перечисления на слайде всех методов как «применённых». Дополнительные первичные материалы: [XP](https://agilealliance.org/glossary/xp/), [Lean](https://www.lean.org/explore-lean/what-is-lean/), [OpenUP](https://archive.eclipse.org/epf/downloads/OpenUP/published/openup_published_1.5.1.5_20121212/openup/publish.openup.base/customcategories/understanding_openup_A45D6188.html), [MSF](https://www.microsoft.com/en-us/download/details.aspx?id=3214), [DSDM](https://www.agilebusiness.org/resource/the-dsdm-agile-project-framework/), [Cleanroom](https://www.sei.cmu.edu/library/cleanroom-software-engineering-reference/).

## 6. Архитектура, модели и данные

В проекте небольшие компоненты имеют отдельную ответственность: данные результата, публичное состояние сеанса, границы внешних моделей и аудиоустройства, хранение, интерфейс. Это позволяет проверять поведение без обязательного открытия окна и заменять технологию за понятной границей. Состав и реальные операции нужно сверять с исходниками, а не заучивать по схеме старого приложения.

Пользовательский вариант использования описывает, кто и зачем взаимодействует с приложением. Для нас это «подготовить два раздела по записи», а не пример бронирования из лекции. Обычная последовательность: выбрать вход → начать обработку → получить транскрипцию → получить сведения → проверить → исправить → экспортировать. Ошибочные ветви и повторная попытка описываются отдельно. Модель данных показывает, какие сущности храним: входной файл, транскрипцию, сведения с разделами и источниками, правки, настройки и статус. Модель компонентов показывает ответственность и взаимодействие.

Слово «модель» имеет здесь три разных значения:

1. **Модель жизненного цикла** — организация разработки, например инкрементная.
2. **Модель системы** — упрощённое описание структуры или поведения, например схема компонентов и переходов.
3. **Обученная модель** — параметры машинного обучения, которые используются для распознавания или извлечения.

Распознавание и понимание естественной речи слабо формализуемы: трудно описать полный набор правил для всех голосов, шумов и формулировок. Это основание применять обученные модели и измерять ошибки на данных. При этом управление записью, чтение файла и сохранение правок имеют чётко проверяемое поведение. Не следует называть всё приложение одной непредсказуемой задачей.

CRISP-DM описывает работу с аналитической задачей: понимание цели, понимание данных, подготовку, моделирование, оценку и применение. В нашем проекте полезны формулировка задачи, проверка данных и независимая оценка. Использование готовых моделей не является обучением собственной модели. Если обучения нет, не изображаем подбор параметров обучения, обучающие эпохи или точность «на обучении».

Логистическая регрессия и дерево решений на лекционном примере не обязательны для нашего аудио. Кандидаты подбираются под операцию: распознавание речи, извлечение сведений или продуктовый сценарий. Простейшим исходным порядком работы может служить существующая ручная подготовка разделов; выдумывать медицинский классификатор ради слова «базовый» не нужно.

CASE — средства поддержки инженерной работы: требования, модели, код, версии, связи и проверки. Использование репозитория, инструментов разработки и диаграммы может поддерживать отдельные задачи CASE. Не требуется внедрять специальную тяжёлую систему, чтобы упомянуть термин. GitHub хранит задачи и изменения, а не автоматически обеспечивает правильность требований.

Изучить: лекция 2.1, слайды 2–4, 7–17, 22, 27–32. Дополнительно: [обзор CRISP-DM от IBM](https://www.ibm.com/docs/en/spss-modeler/18.6.0?topic=dm-crisp-help-overview).

## 7. Качество и метрики

ISO — Международная организация по стандартизации, IEC — Международная электротехническая комиссия. Совместный стандарт ISO/IEC 25010:2023 предлагает модель качества продукта из девяти характеристик. Использование терминов стандарта не означает сертификацию, соответствие медицинским нормам или клиническую готовность. Источник: [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html).

| Характеристика | Применение к нашей версии |
|---|---|
| Функциональная пригодность | Реализованы нужные операции; сведения и разделы соответствуют исходному разговору |
| Эффективность производительности | Известны время обработки и необходимые ресурсы на указанном ПК |
| Совместимость | Известны поддерживаемые форматы и способы обмена. Будущая интеграция с 1С ещё не доказана |
| Способность к взаимодействию | Пользователь понимает состояния, может просмотреть источник и исправить результат |
| Надёжность | Ошибки обнаруживаются и обрабатываются; следующая попытка возможна; результаты сеансов не смешиваются |
| Защищённость | Известны места хранения, сетевые обращения и доступ к файлам; чувствительный текст не скрыто уходит в журналы |
| Сопровождаемость | Ответственности разделены, код и инструкции понятны, изменения проверяются |
| Гибкость | Программа приспосабливается к заявленным условиям и заменам компонентов; переносимость требует проверки |
| Безопасность | Пользователь проверяет черновик; ошибки модели не должны незаметно становиться утверждённым протоколом |

Локальность не защищает автоматически от чтения файлов другим пользователем ПК. Микрофон телефона как источник файла не доказывает наличие мобильного приложения. Защищённость данных и предотвращение вреда от неправильного содержания — разные вопросы.

Для качества распознавания используем WER: `(замены + пропуски + вставки) / слова эталона`. Для представления в процентах умножаем на 100. Показатель может быть больше 100%, например при большом числе вставок. Для всего набора складываем ошибки и слова, а не усредняем проценты файлов без учёта их длины. Эталон с нулём слов нельзя использовать в обычной формуле; тишину проверяем отдельным случаем.

WER применяется к дословной транскрипции. Сравнивать этим показателем краткое резюме с полным разговором некорректно. Нормализацию регистра, пунктуации и чисел фиксируем заранее. Удаление медицински важных отрицаний ради улучшения числа недопустимо. Источник: [описание WER](https://huggingface.co/spaces/evaluate-metric/wer/blob/main/README.md).

Для выделения сведений считаем точность: `правильные выданные / все выданные`, и полноту: `правильные выданные / все ожидаемые`. До получения ответов определяем отдельное сведение, правильный смысл, правильный раздел, допустимый источник и обработку дублей. Наличие цитаты в транскрипции подтверждает её происхождение, но не правильность отнесения к жалобам или анамнезу. Само извлечение проверяем на эталонном тексте, всю цепочку — на аудио.

Если знаменатель равен нулю, не подставляем незаметно 100%. Правило такого случая фиксируется, а рядом приводятся исходные количества. Ошибки отрицания, числа, стороны тела и неподтверждённые сведения разбираем отдельно: одинаковое количество ошибок в WER может иметь очень разные последствия.

Для времени задаём начало и конец. При измерении всей цепочки начинаем перед запуском обработки выбранного файла, заканчиваем после получения всего результата. Загрузку моделей учитываем отдельно. В `faster-whisper` нужно перебрать все сегменты: создание генератора ещё не означает завершённую транскрипцию. Время пользователя до исправленного результата — отдельная метрика, требующая реальных действий человека. Источник: [faster-whisper](https://github.com/SYSTRAN/faster-whisper).

RTF — время обработки, делённое на длительность аудио. Он безразмерный: 120 секунд обработки 600 секунд аудио дают 0,2. Отношение учитывает длину, но не уравнивает сложность записей. Для повторов приводим число запусков, медиану и разброс; три запуска одного файла не являются тремя независимыми диалогами.

| Поле карточки метрики | Что фиксируем |
|---|---|
| Объект | Транскрипция, сведения, отдельная обработка или пользовательская задача |
| Единица | Проценты, секунды, число завершений, отношение времени |
| Метод | Формула, скрипт, правило ручной разметки, начало и конец таймера |
| Условия | Версии, модель, настройки, ПК, устройство, данные, загрузка и сеть |
| Период | Каждый экспериментальный запуск или отдельная пользовательская проверка |

Обоснованная метрика применима к вопросу, объективно считается, повторяется и воспроизводится, замечает важные изменения, практически доступна и не создаёт ложной точности. WER измеряет ошибки слов, но не всю клиническую пригодность. Вывод «программа надёжна на 95%» нельзя делать из доли завершённых запусков маленького набора.

Сбор данных — журналы операций и измерений, сохранённые ответы, проверенные эталоны, наблюдение за задачей пользователя. Анализ — сравнение с требованиями, разбор причин ошибок и различий продуктов. Аудит, статистический анализ и пользовательское исследование не являются обязательными взаимозаменяемыми названиями одного прогона. Формальный аудит отдельно не заявлен; описательная статистика времени полезна; наблюдение за реальным пользователем требует его участия.

Изучить: лекция 1, слайды 50–58; лекция 4, слайды 10–16. Предельные значения качества и времени для больницы пока не согласованы: итоговый отчёт даёт результаты и ограничения, не выдуманную норму.

## 8. Данные, утечка и честное сравнение

Подготовка данных включает отбор подходящих вымышленных сценариев, проверку аудиофайлов, создание эталонной расшифровки и разметки, связь артефактов по ID. Сведения о записи — длительность, источник голоса, микрофон или синтезатор, условия, версия. Ошибки файлов и исключения сохраняются в журнале. Трудный пример нельзя удалить только потому, что он ухудшает показатель.

Сценарий, который собирались произнести, и фактически произнесённая речь могут различаться. Эталон должен соответствовать аудио. Независимая проверка вторым человеком уменьшает ошибки разметки; спорные медицинские разделы требуют предметного специалиста. Синтезированный голос подходит для технической воспроизводимости, но ограничивает выводы о реальном разговоре.

Утечка данных в эксперименте означает попадание правильных ответов или сведений из будущего в настройку и вход. Для готовой модели сохраняем отдельные примеры разработки и итоговой оценки. При обучении добавляются обучающая и валидационная части. Варианты одного сценария держим вместе. Если заявляем новые голоса, в тесте нужны участники, не участвовавшие в настройке. Источник: [предотвращение утечки данных](https://scikit-learn.org/stable/common_pitfalls.html).

Поскольку обрабатываем завершённую запись, все её реплики доступны одновременно. Поздняя реплика этой записи не является запрещённой информацией из будущего. Исправленная итоговая форма, поданная в модель при оценке первоначального извлечения, уже содержит ответ и искажает проверку.

Раскрытие личных данных — другой смысл слова «утечка». В учебной работе используем вымышленные данные; это не отменяет необходимости понимать хранение и сетевые обращения продукта. Дообучение на реальных диалогах не входит в этот комплект.

При сравнении различаем **продукты**, **модели** и **исходный пользовательский порядок работы**. Продукт включает интерфейс и сценарий; модель решает отдельную операцию. Одинаковая модель внутри двух приложений не делает продуктовый эксперимент бессмысленным, но ограничивает объяснение различий.

| Проверка кандидата | Для чего |
|---|---|
| Реальная локальная работа | Соответствие установленному ограничению |
| Русская речь и нужный результат | Сопоставимость с задачей |
| Общая операция и одинаковый вход | Справедливое сравнение |
| Доступность запуска и настройки | Возможность измерить, а не пересказать сайт |
| Фиксированные версии и параметры | Воспроизводимость |
| Сохранённые ответы и ошибки запуска | Проверяемость выводов |

FreeScribe и Open Medical Scribe рассматриваются как кандидаты близкого медицинского сценария. Buzz и vosk-transcriber полезны для сравнения транскрипции; способность выполнять дополнительную локальную обработку проверяется в конкретной версии. Если кандидат не запускается или не подходит по языку, это причина исключения, а не нулевой балл качества. Результат отбора и фактические прогоны находятся в итоговом отчёте.

Первичные описания кандидатов: [FreeScribe](https://github.com/ClinicianFOCUS/FreeScribe), [Open Medical Scribe](https://github.com/BirgerMoell/open-medical-scribe), [Buzz](https://chidiwilliams.github.io/buzz/docs), [Vosk](https://alphacephei.com/vosk/install). Документация даёт основание для отбора; эксперимент даёт основание для измеренного сравнения.

Нельзя сравнивать время одной транскрипции со временем полной цепочки, использовать более лёгкие записи только для своего продукта или менять критерий после просмотра ответа. Необходима оговорка: модель, настройки, аппаратная платформа и набор данных влияют на вывод. Универсальное превосходство по небольшому учебному прогону не устанавливается.

## 9. Что означает тестирование

Тестирование помогает оценить качество, обнаружить несоответствия и уменьшить риск. При динамической проверке сравнивают фактический результат с ожидаемым; статические проверки исследуют требования, данные или код без выполнения проверяемого приложения. Найденное несоответствие требует анализа: причиной может быть дефект кода, ошибочный эталон, неверная проверка или среда.

QA — организация работы для обеспечения качества: проверяемые требования, рецензирование, ясные изменения и воспроизводимая сборка. QC — оценка конкретного результата: проверки версии, измерения и анализ дефектов. Выбор инкрементной модели помогает организации, но сам по себе не гарантирует качество.

Верификация отвечает, выполнены ли установленные требования. Валидация отвечает, пригодно ли решение для потребности пользователя в контексте применения. Она не является более поверхностной. Проверка запускаемой программы по требованию может быть верификацией; обсуждение макета с пользователем помогает валидации до реализации. Поэтому нельзя строго приравнивать статическое к верификации, динамическое — к валидации.

| Принцип | Значение для нашего проекта |
|---|---|
| Тесты обнаруживают дефекты, но не доказывают их полное отсутствие | Пройденный набор не гарантирует правильность любого диалога |
| Перебрать всё невозможно | Выбираем классы файлов, состояния, значимые аудиоситуации и риски |
| Проверять полезно рано | Рецензируем требования и эталоны, готовим сценарии до реализации |
| Проблемы часто сосредоточены в отдельных местах | По наблюдениям усиливаем проверки управления состоянием или другого проблемного участка |
| Старый набор теряет способность находить новые разновидности проблем | Полезную регрессию сохраняем, новые случаи добавляем по рискам и наблюдениям |
| Контекст влияет на выбор | Для аудиомодуля особенно важны смысл, источник, потеря правок и восстановление |
| Выполнение записанных требований ещё не гарантирует пользу | Врач должен суметь использовать и проверить результат |

Исчерпывающая проверка невозможна из-за сочетаний голосов, шумов, файлов, устройств, формулировок и состояний. Скопление дефектов не означает, что один прогон обнаружит их все. Принцип об отсутствии ошибок не утверждает, что в любой программе непременно есть дефект; он ограничивает вывод из успешных проверок.

Основной дополнительный источник: [ISTQB Foundation Level 4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf). Изучить: лекция 4, слайды 2–9 и 22–32.

## 10. Как классифицируются наши проверки

Классификации пересекаются. Один ручной импорт файла через интерфейс может быть динамической, системной, функциональной, позитивной проверкой по внешней спецификации.

| Основание | Варианты и пример |
|---|---|
| Выполнение приложения | Статическое рецензирование требований и кода; динамический запуск функции |
| Уровень | Компонентная проверка части; интеграционная проверка связи; системный сценарий приложения; приёмка пользователем |
| Цель | Функции, производительность, удобство, восстановление, локальность и другие согласованные качества |
| Способ выполнения | Действия человека или автоматическое выполнение и сравнение |
| Основа выбора | Чёрный ящик — требования и внешнее поведение; белый — структура и ветви кода; серый — частичное знание устройства |
| Данные | Позитивный корректный вход; негативный недопустимый вход или условие |
| Повторение после изменения | Подтверждение исправления или регрессия |

Чёрный ящик не требует незнания кода. Доступ к исходникам не делает любой тест белым ящиком. Статический анализатор запускается как инструмент, но исследуемое приложение не исполняется. Статистический анализ чисел отличается от статического анализа кода.

Учебный «модуль ВКР» содержит несколько компонентов. Проверка всей аудиоцепочки системная относительно этого приложения. Изолированная сборка сегментов — компонентная. Чтение файла и передача аудио обработчику — интеграционная. Уровень зависит от границы объекта проверки, а не от названия проекта.

Классы эквивалентности помогают выбрать представителей: корректный файл, повреждённый, неподдерживаемый. Переходы состояний помогают проверить «готовность → запись → обработка → результат» и восстановление после ошибки. Граничные значения используем только для реально установленных пределов. Исследовательское тестирование дополняет сценарии целевым изучением области, например повторных запусков, с записью наблюдений.

Ожидаемый успешный результат негативного теста может быть отказом с понятным сообщением. Негативных проверок не обязано быть больше позитивных. Важность дефекта зависит от последствий, а не от удобства входного примера.

Для быстрой автоматизации выбраны наблюдаемые операции сеанса, чтение/сохранение и реакции на внешнюю ошибку. Для качества моделей — отдельный эксперимент с настоящими локальными моделями. Для микрофона и удобства — ручные сценарии. Тесты с подставленной моделью и оценка реальной модели отвечают на разные вопросы; один результат другим не заменяется.

## 11. Порядок проверки, отчёт и дефекты

Процесс проверки проходит через анализ продукта и рисков, работу с требованиями, планирование, подготовку сценариев и данных, пробы прототипов, основной прогон, стабилизацию и дальнейшее наблюдение. На каждом инкременте выполняется нужная часть этого процесса. Непроведённая эксплуатация в больнице так и обозначается.

Тест-план должен содержать 16 полей лекции 4, слайда 15: ID; введение; объект; проверяемые функции; исключения; подход; критерии прохождения; условия остановки и возобновления; выходные материалы; задачи; среду; обязанности; потребности в исполнителях и знаниях; расписание; риски и меры; согласования. Английское `Test deliverables` означает выходные материалы, а не заранее написанные успешные результаты.

Карточка случая связывает требование, цель, предусловия, данные, шаги и ожидаемый результат. После выполнения добавляются факт, статус, версия, среда, исполнитель и подтверждение. Статусы «не пройден», «не выполнен» и «заблокирован» не сводятся к успешному завершению. Для автоматизации сохраняется команда и журнал.

Отчёт о тестировании по слайду 19 включает: состав команды; период; процессы; изменения сценариев; долю пройденных случаев с исходными количествами; критические и блокирующие проблемы и меры; результаты регрессии и открытые проблемы; следующий шаг. Число методов в коде может отличаться от числа наборов данных или запусков, поэтому единицу подсчёта указываем.

Отчёт о реальном дефекте по слайду 20 содержит ID, краткое и подробное описание, шаги, фактический и ожидаемый результат, вложения, серьёзность, приоритет, статус и окружение. Серьёзность — влияние, приоритет — очередность исправления. В учебной команде issue может быть таким отчётом. Отсутствие найденных дефектов не даёт права придумывать один ради документа.

Пример различия проверок после изменения: если исчезали правки при переключении экрана, повторяем именно это действие — подтверждаем исправление. Затем проверяем первоначальный показ текста, другие переходы и начало нового диалога — ищем регрессию. Нарушить прежнее поведение может изменение программы; регрессия помогает это заметить.

Результаты относятся к версии приложения, моделей, данных и условиям. Если версия B исправила дефект A, нужны повторные результаты на B. Если в C затронута та же область, успешный тест B не подтверждает её автоматически. Обработка за минуту на одном ПК не доказывает ту же скорость на другом. Дата полезна, но за один день возможны разные версии; нужен коммит или идентификатор сборки.

В среде фиксируем ОС, Python и зависимости, CPU/GPU и память, модели и параметры, аудиоустройство и условия записи, данные и сеть. Локальное приложение не обязывает создавать отдельные серверы для каждой среды из лекции. Но необходимо различать локальный запуск, CI, пользовательскую проверку и эксплуатацию.

Решение о завершении может быть «готово с ограничениями» или «не готово». Отчёт с открытым блокирующим дефектом допустим как честный результат, но такую версию нельзя объявлять готовой по критериям, запрещающим этот дефект. При изменении сценария после найденной проблемы причина записывается; критерий не подгоняется ради зелёной строки.

## 12. Что студенты должны проверить лично

Инструментальная автоматизация и запуск агентом должны иметь соответствующее обозначение. Их нельзя подписывать как выполненную Михаилом или Юрием ручную проверку. Ручной запуск команды автоматических тестов оставляет сами тесты автоматизированными.

Минимальные личные сценарии: запись настоящим микрофоном; импорт и сверка эталонного диалога; редактирование и переходы; недоступный микрофон и повтор; отзывчивость при обработке; работа без сети после подготовки моделей. Для каждого нужны фактический результат, дата, версия, среда и исполнитель. Если проверка ещё не выполнена, статус остаётся открытым.

Представитель предметной области нужен для оценки медицинской разметки и полезности результата. Студент может проверить перенос известной цитаты, но его согласие не заменяет клиническую приёмку. Секунды работы врача не измеряются симуляцией пользователя. Синтетические голоса не обозначаются записью разговора студентов.

## 13. Вопросы для подготовки к защите

| Вопрос | Основа ответа |
|---|---|
| Что вы разработали? | Назвать согласованную цепочку и два раздела; показать реальный сценарий |
| Зачем выделяли часть ВКР? | У неё законченный результат и проверяемый объём; остальные обещания не выдаются за реализованные |
| Почему инкрементная модель? | Поставляются отдельные возможности; уточнения и проверки происходят внутри развития |
| Почему не водопадная? | Возможна при стабильном полном задании; наш план ориентирован на ранние результаты и уточнения |
| Где Agile? | Назвать конкретное решение по обратной связи или ограничению лишней работы и показать доказательство |
| Где Scrum? | Полный Scrum не заявлен; используются выбранные Kanban-практики |
| В чём TDD? | Показать один реальный тест, ожидаемое падение, изменение и успешный прогон |
| Что доказывает подставленная модель? | Поведение нашего кода на известном внешнем ответе; качество модели оценивается отдельно |
| Вы обучили нейросеть? | Используются готовые локальные модели; дообучение не заявлено без фактического цикла |
| Почему выбран этот аналог? | Общая операция, локальность, русский язык, доступность запуска; затем реальные ограничения |
| Почему WER недостаточно? | Он считает ошибки слов, но не правильность раздела и медицинского смысла |
| Откуда правильный ответ? | Из проверенной расшифровки и заранее подготовленной разметки; статус предметной проверки указан |
| Почему эти тесты? | Каждый связан с требованием и риском; количество само по себе не цель |
| Чем отличается регрессия? | Проверяет прежнее связанное поведение после изменения; повторный тест подтверждает конкретное исправление |
| Можно ли использовать в реанимации? | Учебная техническая проверка не является клинической готовностью; нужны согласование и реальные условия |
| Всё ли прошло? | Отвечать по конкретному отчёту, включая невыполненные, заблокированные и ручные случаи |
| Чем вы подтвердили ускорение работы? | Только реальным измерением одинаковой пользовательской задачи; если его нет, сказать, что эффект пока не измерен |

При объяснении любого теста достаточно последовательно назвать требование, риск, данные, ожидаемый результат, фактический результат и границу вывода. При объяснении измерения — что сравнивали, в каких условиях, как считали и чего этот показатель не устанавливает.
