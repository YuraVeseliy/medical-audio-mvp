# План тестирования TP-ASR-02

Дата: 25.10.2026. Объект: версия 0.2 модуля полной транскрибации. Это рабочий план учебной проверки, а не заключение о готовности медицинского изделия.

## Поля плана

| Поле | Решение для модуля |
|---|---|
| Идентификатор | TP-ASR-02; требования FR01–FR07, NFR01–NFR03 из asr-plan.md |
| Введение | Проверить пользовательскую цепочку от аудио до сохранённого полного текста и измерить различия восьми локальных ASR |
| Объект | Python/Tkinter-приложение, Session, декодирование, адаптеры ASR, файлы сеанса, скрипт сравнения |
| Проверяемые функции | Явная запись и остановка, импорт, выбор ASR, весь текст, правка, JSON/TXT, восстановление, ошибки и защита несохранённого результата |
| Непроверяемые функции | Диагноз, заполнение разделов формы, 1С, телефонный клиент, идентификация пациента; их нет в данном модуле |
| Подходы | Ревью требований/кода; публичные автоматические проверки; реальный GUI-сценарий; сравнение на проверенных эталонах; личные ручные карточки |
| Критерии прохождения | Быстрые проверки без ошибок и пропусков; GUI круговой сценарий сохраняет исходник и правки; замеры воспроизводимы. Для кандидата обязательны все запланированные обработки; выбор по правилу в asr-plan.md. Клинический порог WER не установлен |
| Приостановление | Повреждены или изменились данные/веса/исходники; не подтверждены TXT; закончилась память/место; повторяющийся сбой мешает сценарию |
| Возобновление | Причина установлена, исправление проверено; новый каталог результата, при изменении данных новый манифест. Прерванный журнал сохраняется |
| Выходные материалы | tests.log, summary.json; red/green; GUI JSON/TXT; freeze/rows/summary и исходные ответы ASR; карточки ручных проверок; дефекты и итоговый отчёт |
| Задачи | Подготовка окружения → проверка эталонов → быстрые тесты → dev-пробы → selection → контроль победителя → личная ручная проверка → отчёт |
| Ресурсы | Windows x64, Python 3.12 с Tk, зависимости lock, CPU/RAM из freeze.json; модели из каталога и манифестов; 10 вымышленных записей. Для M04 требуется настоящий микрофон |
| Обязанности | Агент реализует и выполняет инструментальные прогоны. Юрий подтвердил TXT по звуку. Юрий и Михаил лично запускают проверки, читают тесты и выполняют карточки. Врачебная приёмка отдельно, не заявлена |
| Расписание | Этапы выполняются по зависимостям выше. Даты фактических прогонов берутся из UTC-журналов; согласованный срок приёмки заказчиком отсутствует |
| Риски | Один читатель, короткие записи, неуточнённый диктофон; ошибки чисел/отрицаний; влияние фоновых процессов и нагрева; различия декодеров; время скачивания; ложное впечатление качества по зелёным тестам с подставным ASR |

## Что проверяют 15 автоматических тестов

Это 15 понятных проверок, а не требование объяснять десятки не связанных с модулем случаев. Подставной внешний ASR выдаёт известный текст, чтобы ошибка модели не мешала проверять управление приложением. Реальные Session, декодирование и запись файлов исполняются. Качество настоящих моделей измеряется другим экспериментом.

| ID | Вход и действие | Ожидаемый результат; зачем |
|---|---|---|
| T01 | WAV + внешний ASR с тремя репликами; process_file | Все реплики в исходном/редактируемом тексте и модель в метаданных; обязательный LLM не вызывается |
| T02 | Получить текст, исправить, сохранить JSON/TXT, открыть | Правка восстановилась, исходник сохранён, TXT совпадает с текущим текстом; проверка интеграции сеанса и файлов |
| T03 | Повреждённый аудиофайл | Понятная AppError; случайные байты не выдаются за запись |
| T04 | Декодируемый файл, ASR не вернул слов | Сообщение о пустом результате; отсутствие слов не выдаётся за успех |
| T05 | Внешний ASR падает один раз, затем отвечает | Повторная обработка возможна; ошибка не блокирует сеанс навсегда |
| T06 | Новый сеанс при несохранённом тексте | Без явного force результат не теряется; проверка защиты данных |
| T07 | ASR ожидает освобождения, вызвана вторая обработка | Вторая операция отклонена; конкурентные результаты не смешиваются |
| T08 | При открытом результате загрузить испорченный JSON | Ошибка формата не заменяет текущий документ |
| T09 | Настоящий IEEE FLOAT WAV | Файл декодируется и доходит до ASR; регрессия прежнего дефекта импорта |
| T10 | Остановить запись, отменить выбор пути; внешний адаптер микрофона | В момент диалога захват уже остановлен, буфер не потерян; регрессия D01 |
| T11 | 24 секунды PCM с маркером последнего отсчёта | Внешний backend получает все отсчёты по порядку, последний маркер доходит, фрагменты ≤20 секунд; полная обработка длинного файла |
| T12 | Эталон «у меня болит левая рука», ответ «у меня сильно болит правая рука» | 1 замена + 1 вставка, 5 слов, WER=2/5=0,4; известный независимый пример расчёта |
| T13 | Одинаковый звук в разных группах, с пометкой дубликата и без неё | Набор отклонён по реальному PCM; не допускаем утечку между группами |
| T14 | Контроль с прежними и затем изменёнными потоками/отпечатками весов | Неизменный вариант принят, изменённые отклонены; контроль относится к действительно выбранной конфигурации |
| T15 | Worker прерван после одной сохранённой строки | Завершённая строка восстановлена, пропуски не исчезли, кандидат не выбран, память помечена неполной |

Только T01, T02, T12, T13, T14 и T15 имеют сохранённые последовательные red/green циклы этой разработки. Другие проверки - регрессии/проверки после реализации; их нельзя выдавать за TDD. Расширение признака неполной памяти в T15 добавлено при ревью после реализации.

## Уровни и виды

T12 - проверка отдельного вычисления. T01–T09 и T11 - интеграция публичного сеанса с файлами и внешней границей; называть весь модуль одним unit-тестом неверно. T10 и check_gui_scenario.py используют настоящее окно Tkinter, но внешние устройство/модель могут быть подставлены. Прогон check_gui_scenario.py с --model использует настоящую модель и проверяет управляемый GUI путь. Человек отдельно выполняет M01–M08 из manual-tests.md.

Позитивные случаи: правильный файл, правка и восстановление. Негативные: повреждение, пустой ответ, сбой, конфликт, дубликат и изменение условий. Регрессии: прежние дефекты остановки и FLOAT WAV. Производительность: секунды, RTF, RSS в реальном ASR-прогоне. Статическое тестирование - ревью и анализ типов без запуска пользовательского сценария. Динамическое - выполнение программы. Ручное/автоматическое, уровень и цель - разные классификации, их можно сочетать.

Полноценные нагрузочные, клинические, пентест и исследования удобства с врачами не проводились. Для них нет согласованной среды/пользователей/нагрузки. Малый учебный эксперимент этого не заменяет.

## Как выполнить самому

После setup.cmd открыть PowerShell в корне проекта и выполнить:

```powershell
.\.venv\Scripts\python.exe scripts\check.py --out user_data\yuri-checks-01
```

Человек запускает команду, а проверки и сравнение с ожиданиями выполняет программа. Это самостоятельное выполнение автоматизированного тестирования. Сохранить tests.log/summary.json; прочитать один тест, показать вход, вызов, assert и результат. Для Михаила - другое имя папки, собственный фактический запуск. Если есть failure, показать traceback, вход, ожидаемое и фактическое, завести дефект.

Проверка исправления повторяет конкретные шаги дефекта. Регрессия после этого проверяет другие важные функции, которые могло затронуть исправление. Зелёный результат относится к указанной версии и условиям, поскольку другой код, библиотека, устройство или файл меняют то, что проверялось.
