Период: 24–25.10.2026. Среда: Windows 10 build 19045, Python 3.12.14 x64, Tk 8.6.12, CPU Ryzen 7 5800H. Дефекты найдены рецензированием и воспроизведены инструментально; настоящая запись с микрофона не включалась. Код до исправления: 9fc14e3. Поля соответствуют лекции 4, слайд 20.

## D01 — Микрофон продолжает захват после нажатия остановки

- ID: D01 (локальный; GitHub issue не опубликована).
- Название: «Остановить и сохранить» открывает диалог пути до остановки захвата.
- Описание: до исправления GUI вызывал recorder.stop только после выбора файла. Пока открыт диалог сохранения, захват продолжался; отмена оставляла запись активной.
- Предусловия: идёт запись; устройство заменено тестовым внешним адаптером с тем же публичным состоянием, без захвата окружающей речи.
- Шаги: открыть приложение с адаптером в recording → нажать остановку → в диалоге отменить выбор файла.
- Ожидаемый результат: захват остановлен перед выбором пути; при отмене остаётся captured-буфер, который можно сохранить повторно или явно удалить.
- Фактический результат до исправления: state_at_dialog=recording; после отмены запись остаётся recording.
- Вложения: reports/defects/D01/before.log; tests/test_regressions.py, test_d01_cancel_save_dialog_keeps_stopped_recording.
- Серьёзность: средняя: неожиданное продолжение захвата и лишний звук после ожидаемой остановки.
- Приоритет: P2, исправить до выдачи учебного комплекта.
- Статус: исправлен; исходный сценарий повторно пройден.
- Исправление: AudioRecorder.capture останавливает и закрывает поток, сохраняя буфер; GUI сначала выполняет capture, затем спрашивает путь. Отмена не возобновляет захват.
- Подтверждение исправления: reports/defects/D01/after.log.
- Регрессия: общий набор 10/10; проверены сохранение/восстановление, новый сеанс, исключения и защита конфликтующих операций. Рецензент дополнительно проверил идемпотентный capture с тестовым внешним потоком.
- Ограничение: остановку настоящего устройства нужно проверить в M01/M04; это не записано как выполненное студентами.

## D02 — Корректный FLOAT WAV ошибочно отклоняется

- ID: D02 (локальный; GitHub issue не опубликована).
- Название: импорт WAV с IEEE_FLOAT format 3 завершается ошибкой предварительной проверки.
- Описание: Session использовал stdlib wave.open, поддерживающий не все заявленные WAV-подтипы. Корректный FLOAT WAV не доходил до распознавателя.
- Предусловия: файл tests/fixtures/float32.wav, 16 kHz mono FLOAT, создан библиотекой soundfile; внешние нейросетевые ответы в проверке подставлены.
- Шаги: Session.process_file на этом файле.
- Ожидаемый результат: декодируемый WAV принимается как вход; дальнейшая цепочка обрабатывает его.
- Фактический результат до исправления: wave.Error unknown format: 3, затем AppError «Не удалось открыть аудиофайл».
- Вложения: reports/defects/D02/before.log, fixture и test_d02_valid_float_wav_is_supported.
- Серьёзность: средняя: один из корректных поддерживаемых файлов невозможно загрузить.
- Приоритет: P2, исправить до выдачи учебного комплекта.
- Статус: исправлен; повторная проверка пройдена.
- Исправление: PyAV проверяет наличие аудиопотока и декодирует первый кадр вместо ограничения stdlib wave. AV закреплён в зависимостях и CI.
- Подтверждение исправления: reports/defects/D02/after.log.
- Регрессия: общий набор 10/10, в том числе повреждённый файл по-прежнему отклоняется.
- Ограничение: короткий fixture проверяет приём формата, а не точность ASR на float-аудио с речью.

## D03 — Установка ASR не работает с неподходящей версией setuptools

- ID: D03, проблема совместимости зависимостей.
- Описание: установленный setuptools 84 не предоставлял pkg_resources, который импортировала зависимость используемой конфигурации ASR. Первый настоящий запуск эксперимента завершался до распознавания.
- Среда: Windows/Python 3.12, исходная конфигурация пакетов; модели уже загружены.
- Шаги: установить исходные зависимости → запустить ASR-development через compare_local.py.
- Ожидается: загрузка модели и распознавание учебного WAV.
- Фактически: ModuleNotFoundError: No module named 'pkg_resources'.
- Вложения: reports/comparison-asr-fw-development/environment.json и comparison-asr-fw-development2/environment.json.
- Серьёзность: высокая для воспроизведения — блокирует запуск конкретной установленной конфигурации. Приоритет: исправить до передачи проекта.
- Исправление: закрепить setuptools==80.9.0 в requirements.txt. Это исправление окружения, а не точности распознавания.
- Подтверждение: reports/comparison-asr-fw-development3/environment.json; последующий полный ASR-прогон завершил 18/18 попыток (reports/comparison-asr-fw/results.json).
- Статус: исправлено в проверенной конфигурации; на другом ПК требуется повтор установки. Отдельный фиктивный unittest для установленной версии пакета не добавлялся.

## D04 — При отказе извлечения теряется уже полученная транскрипция

- ID: D04, локальный дефект сеанса и отображения.
- Описание: документ создавался только после успешного ответа LLM. Если ASR уже завершилась, а извлечение упало, новая транскрипция не сохранялась; на уровне Session мог оставаться прежний документ.
- Среда: Windows/Python/Tk, до исправления bb01890 с добавленным регрессионным тестом. Внешние ASR/LLM заменены контролируемыми ответами.
- Шаги: получить первый результат → начать обработку другого файла → распознать новый текст → вызвать ошибку внешней LLM → попытаться просмотреть/сохранить новый текст.
- Ожидается: сообщение об отказе распределения, новый исходный текст доступен, разделы пусты, старый результат не выдаётся за новый; можно сохранить и заполнить вручную.
- Фактически: self.document оставался предыдущим объектом; новый исходник отсутствовал. Красный тест зафиксировал AssertionError на проверке нового объекта.
- Вложения: reports/defects/D04/before.log; tests/test_regressions.py, test_d04_extraction_failure_keeps_new_transcript_visible_and_saveable.
- Серьёзность: средняя — потеря полезного промежуточного результата и риск перепутать сеансы. Приоритет: исправить до выдачи комплекта.
- Исправление: создать частичный документ после ASR до извлечения; при отказе сохранить текст, пустые разделы и предупреждение, dirty=true; GUI показывает новый объект и сбрасывает путь прежнего сеанса.
- Подтверждение исправления: reports/defects/D04/after.log — исходный сценарий, отображение и сохранение/восстановление пройдены.
- Регрессия: полный набор 11/11, 0 ошибок и 0 пропусков, reports/checks/summary.json.
- Статус: исправлено. Ошибки выбора сведений моделью этим исправлением не устраняются.

## D06 — Оконный EXE не начинает локальную HTTP-обработку

- ID: D06, дефект сборки/локального транспорта.
- Описание: общий urllib.build_opener создавал также неиспользуемый HTTPSHandler. В оконном EXE создание SSLContext завершалось FileNotFoundError ещё до HTTP-запроса к loopback. В исходном Python этот отказ не проявлялся. Отсутствие журнала первого запуска мешало диагностике.
- Среда: Windows 10, PyInstaller 6.16.0, оконная сборка, локальные модели рядом с EXE, development WAV dev01.
- Шаги: запустить MedicalAudio.exe --cli путь/dev01.wav --out папка на исходной сборке.
- Ожидается: запуск собственного локального сервера и создание session.json/result.txt/run.json.
- Фактически: отказ ssl.SSLContext.__new__, выход 1 после добавления диагностики; первая сборка ждала закрытия диалога исключения и была остановлена тестовым контроллером.
- Вложения: reports/portable-smoke-initial-summary.json; portable-smoke-diagnostics-summary.json; reports/defects/D06/before.log; журналы build-final/build-diagnostics.
- Серьёзность: высокая — обработка готовым комплектом заблокирована. Приоритет: P1 до передачи.
- Исправление: клиент loopback HTTP явно создаёт только HTTP-обработчики, без системного прокси и переходов по адресам; в оконном entrypoint стандартные потоки направлены в локальный журнал, исключение CLI завершается с кодом ошибки.
- Подтверждение: настоящий исправленный EXE с собственной .runtime, HF_HUB_OFFLINE=1 и TRANSFORMERS_OFFLINE=1; exit_code=0, 31.46 с общего холодного запуска; созданы три файла. reports/portable-smoke-final-summary.json, portable-smoke-validation.json, defects/D06/after.log.
- Регрессия: 11 быстрых проверок и инструментальный сценарий S01; это не проверка смысловой точности LLM. Визуальная приёмка окна остаётся отдельной личной проверкой.
- Статус: исправлен в проверенном комплекте на машине разработки. Другой ПК остаётся отдельной проверкой. Состав подсказки, веса и способ выбора номеров после опыта B1.1 не менялись; транспортное исправление выполнено позднее.

## Что не выдаётся за дефект приложения

- Первые красные TDD-запуски новых функций — этап разработки, не найденные пользователем дефекты готового продукта.
- Сбой Windows SAPI в ограниченной среде агента — проблема среды подготовки данных; он привёл к выбору Piper и не объявляется ошибкой продукта.
- PermissionError временных каталогов Python 3.12 в ограниченном токене среды — проблема установки; воспроизводимый bootstrap сохранён отдельно.
- Отсутствие проверки врачом, малый синтетический набор и ограничение контекста модели — раскрытые ограничения оценки/версии. Они не закрываются фиктивным тестом.
- Ошибки выбора сведений моделей измеряются отдельно от детерминированных проверок GUI/файлов. Подтверждённая проблема выбора записана как открытый D05; она не исключена из отчёта ради зелёного результата.
